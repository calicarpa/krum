# ADR 2026-06-12

This note presents the principles for a 1st very basic implementation of the
orchestration logic. For now, we address the following requirements:
- Be able to run a user-defined function (the simulation code) over various
  ranges of parameters.
- Collect the metrics generated by all the runs.
- Be able to select any slice of those metrics for plotting.

In this 1st implementation,
- we **do not** consider persisence issues: all data reside in memory;
- we **do not** consider re-executions of failed runs or runs whose simulation
  code have changed since the last run.

## Guiding example

The package `orchestration` defines (for now) the following classes
- `Orchestrator`
- `Metric`
- `MetricDataFrame`

We illustrate the requirements on these two classes using the following
example. The user (e.g. the researcher using our library) wants to run an
experiment with the following parameter ranges
- n: number of workers, from 10 to 100
- f: number of byzantine, from 2 to 5
- aggregator: average, krum and bulyan
- attack: alie, sign flip
- n_steps: 1000

The user script should look as follows.
```python
from krum.orchestration import Orchestrator, Metric
from krum.simulations import MySimulation

def my_experiment(
    n: int,
    f: int,
    aggregator: Aggregator,
    attack: Attack,
    n_steps: int,
    ):
    my_simulation = MySimulation(n=n, f=f, aggregator=aggregator, attack=attack)

    loss = Metric("loss", float32) # type (float32) optional

    for step in range(n_steps):
        my_simulation.step()
        loss_value = ... # obtained from the simulation, or any other way
        loss.push(step, loss_value)

my_orchestrator = Orchestrator("my_prefix_or_whatever")

for n in range(10,100):
    for f in range(2,5):
        for aggregator in [Average, Krum, Bulyan]:
            for attack in [Alie, SignFlip]:
                my_orchestrator.run(my_experiment, n=n, f=f, aggregator=aggregator, attack=attack, n_steps=1000)

loss_data = my_orchestrator.get("loss") # returns a MetricDataFrame
slice = loss_data(n=13, aggregator=Krum)

# then use standard plotting library to plot data from the selected slice
```

## Design principles

About `Metric`
- The user can create any metric in its custom code (function `my_experiment`)
    - a metric is identified by its name
    - cannot create twice a metric with the same name
- The metric acts as a list where the user can push values
    - in a given run, e.g. experiment(n=13, f=3, aggregator=Krum, attack=Alie,
      n_steps=1000), the value is pushed together with the current parameter
      values
    - morally, it is as if the tuple
      (n=13,f=3,aggregator=Krum,attack=Alie,n_steps=1000,step=34,value=2.34)
      were appended to the channel

About getting back the data
- `my_orchestrator.get("loss")` returns a MetricDataFrame
- conceptually, all the metric values can be represented as a data frame, e.g.
    - columns correspond to the experiment parameters: n, f, aggregator,
      attack, step, loss_value
    - each row correspond to a Metric.push in the user-defined function
      (`my_experiment`)
- the dataframe can be sliced to focus on a specific subset of values

nb: We could use panda's DataFrame, but panda is a bit heavy. We defer to
developers' judgement to assess whether implementing our own MetricDataFrame is
preferrable to just using panda's DataFrame.
