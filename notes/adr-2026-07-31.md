# ADR 2026-08-07

## Data Partitioners

Follow-up on [adr-2026-07-24.md].

In a federated learning context, as a user of the library, I want to easily distribute data to the workers, either identically or non-identically distributed.

The package `primitives.data_partitioners` contains the primitives to facilitate the partitioning of datasets. It defines
- the interface `DataPartitioner`
    - single method `partition`
    - returns `Sequence[Dataset]`
- implementations
    - `IidPartitioner`
    - `PerLabelsPartitioner`
    - `DirichletPartitioner`
    - `MixingPartitioner`

The simulation classes (under `simulations`) should be refactored to accept `Sequence[Dataset]`.

Example.
```python
def my_experiment(dp: DataPartitioner, dp_kwargs, ...):
    # ...
    datasets = dp.partition(dp_kwargs)
    my_simulation = MySimulation(datasets=datasets, batch_size, etc...)
    # ...
```

## Details about `MixingPartitioner`

```python

// pseudo-code
class MixingPartitioner:
    def __init__(
        p1: DataPartitioner,
        p2: DataPartitioner,
        gamma: [0,1],
    ):

    def partition():
        // shuffle
        // split dataset in (1-gamma) and gamma
        //      (1-gamma) is p1-partitioned in N sub-datasets
        //      gamma is p2-partitioned in N sub-datasets
        // zip the two lists
        return (1-gamma) * p1  + gamma * p2
```

### Details about `PerLabelsPartitioner`

Parameters
- lambda: iid-ness, value between 0 and 1

Algorithm
- initial dataset D
- sort by labels
- segment in n_shards = f(lambda)
- shuffle shards
- round-robin assign shards to workers

## Orchestration

We cannot perfectly capture the exact runtime dependencies of a run.
We accept some failures
- false positive: a run is marked for a re-run but it is not actually needed
- false negative: a run is not marked for a re-run but it should be
The design decision is to reduce false negatives as much as possible.

The orchestration uses debugger techniques to determine the set of objects that a run (simulation execution) depends on.
Example. On `orchestrator.run(my_experiment)`
- instrument the python runtime to trace my_experiment using a custom function `trace`
- the function `trace` records the objects (location and content hashes) that the function depends on
- a hash key is computed for this run
    - importantly the hash key depends only on the static content of the function
    - it is not necessary to run `my_experiment` to compute the hash key
- the recorded objects are persisted 
    - locally under a sub-folder identified by the hash key

When intenting to run `my_experiment`
- the hash key is computed
- if it is absent from the persistent storage, then re-run
- if it is present
    - recover the objects locations and compute their hash from the actual content
    - if the new hashes are different from the persisted hashes, then re-run

Execution failures: the whole orchestration stops whenever one simulation execution fails.
Example:
- The orchestrator runs (sequentially) 10 simulation executions.
- If the 1st four succeeds and the 5th fails, then we do not run the remaining executions.
- Instead, the orchestrator stops and provide a summary of the global execution to the user.

We postpone the multiprocess parallelism.
